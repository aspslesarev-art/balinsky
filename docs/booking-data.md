# Booking data (estatemarket.io) — рыночные данные для оценки конкурентности объектов

Назначение: когда анализируешь апартаменты/виллу — ВСЕГДА сравнивай объект
с конкурентами по соседству из этих таблиц, а не оценивай в вакууме.

## Что это за данные

В Supabase-проекте **Balinsky** (`ifdgiwxothmcalibmydv`) лежит полная база
краткосрочной аренды Бали, спарсенная с estatemarket.io/booking_data-map:
**21 001 объект с координатами**, полные карточки, комнаты с ценами и
заполняемостью. Данные обновляются автоматически (pg_cron + Edge Function
`booking-data-sync`): карта и снимок истории — ежедневно ~03:00 по Бали,
карточки — по кругу раз в ~7 дней, классификация — ежедневно после синка.

## Таблицы

| Таблица | Что внутри |
|---|---|
| `booking_data_locations` | Все объекты: id, title, occupancy (%, за период), price ($/ночь), lat, lng |
| `booking_data_cards` | Карточка: description, type, star, slug, min/max_price, facilities, raw (полный JSON), **unit_kind, bedrooms, area_sqm** |
| `booking_data_rooms` | Конфигурации комнат: room_type, price, occupancy, max_available |
| `booking_data_history` | Дневные снимки occupancy/цены по объекту (динамика рынка) |
| `booking_data_room_history` | То же на уровне комнат |
| `booking_data_card_errors` | Служебная: карточки, которые не удалось скачать |

## Классификация (booking_data_cards)

- `unit_kind`: `villa` (10 347) · `hotel` (2 704) · `guesthouse` (2 595) ·
  `apartment` (1 568) · `resort` (1 146) · `house` (681) · `hostel` (385) ·
  `aparthotel` (309) · `other` (1 266)
- `bedrooms`: число спален, `0` = студия. «Вилла-однушка» = `unit_kind='villa'
  and bedrooms=1`, «вилла-двушка» = `bedrooms=2`. Заполнено там, где спальни
  извлекаются из типов комнат/описания (виллы — 85%, апартаменты — 87%;
  у отельных номеров спален нет — там NULL, сравнивай по unit_kind).
- `area_sqm`: площадь из описания. ВНИМАНИЕ: источник почти не отдаёт метраж,
  заполнено <1% — на площадь не опирайся, сравнивай по типу и числу спален.

## Готовые функции сравнения (главный инструмент)

```sql
-- Конкуренты в радиусе (метры) от точки, отсортированы по расстоянию:
select * from booking_data_comps(lat, lng, radius_m, unit_kind, bedrooms, limit);
-- пример: виллы-однушки в 1.5 км от точки в Чангу
select * from booking_data_comps(-8.6478, 115.1385, 1500, 'villa', 1, 50);

-- Сводка по району: сегменты (тип × спальни), средняя загрузка, цены p25/медиана/p75
select * from booking_data_area_stats(lat, lng, radius_m);
```

`price`/`min_price`/`max_price` — $/ночь; `occupancy` — заполняемость в %.

## Как оценивать конкурентность объекта (алгоритм)

1. Возьми координаты и сегмент оцениваемого объекта (unit_kind + bedrooms).
2. `booking_data_area_stats(lat, lng, 1500)` — общая картина района:
   сколько объектов в каждом сегменте, какая медианная цена и загрузка.
3. `booking_data_comps(lat, lng, 1500, kind, beds, 50)` — прямые конкуренты.
   Смотри: их occupancy (норма для сегмента?), в какой квартиль цен попадает
   оцениваемая ставка, сколько прямых конкурентов в пешей доступности
   (насыщенность = давление на цену).
4. Динамика: `booking_data_history` по id конкурентов — куда движутся цена
   и загрузка в этом районе (сезонность, тренд).
5. Вывод формулируй так: «В радиусе 1.5 км N вилл-двушек, медиана $X/ночь
   при Y% загрузке; объект по $Z попадает в верхний/нижний квартиль; при
   такой насыщенности ожидаемая загрузка ~...».

Радиусы-ориентиры: плотные районы (Чангу, Семиньяк, Убуд-центр) — 1000–1500 м;
разреженные (Табанан, север) — 3000–5000 м. Если в сегменте <10 объектов,
расширь радиус или убери фильтр bedrooms.

## Ограничения данных — держи в голове

- occupancy/price на `booking_data_locations` — снимок за период показа сайта;
  у ~40% объектов price NULL → используй min_price/max_price из карточки.
- Метраж (area_sqm) почти пуст — не строй на нём сравнение.
- bedrooms NULL у отельных номеров — это не ошибка, сравнивай отели по
  unit_kind и звёздам.
- История копится с 2026-08-05 — тренды станут осмысленными через 2–4 недели.

## Признаки продукта из фотографий (vision-слой)

Цена и загрузка отвечают «сколько», но не «за что». Поэтому фотографии всего
рынка прогнаны через `gpt-5.4` и превращены в 31 признак продукта
(стиль, уровень отделки, тип бассейна, вид, материалы, планировка, качество
съёмки, красные флаги). Словарь признаков — `scripts/_product-vision.mjs`,
он ОБЩИЙ для рынка аренды и нашего каталога, иначе их нельзя сравнивать.

| Объект | Что внутри |
|---|---|
| `booking_data_vision` | id → `vision` jsonb, разбор фото объекта аренды |
| `catalog_product_vision` | наши виллы/апартаменты/ЖК тем же словарём |
| `booking_market_product` | разбор + adr/occupancy/revpar + зона |
| `booking_market_relative` | то же, но в долях от медианы страты «зона × тип × спальни» (`adr_ratio`, `occ_ratio`, `revpar_ratio`) |
| `catalog_product_zone` | объект каталога + его зона |
| `booking_zone(lat,lng)` | 30 именованных зон рынка, дальше 8 км — `'Прочее'` |

**Премию за признак считай ТОЛЬКО через `booking_market_relative`** и страты от
8 объектов: на сырых ценах «инфинити-бассейн» окажется премией за Улувату, а не
за бассейн. Порядки величин (август 2026): отделка уровня 4 → ×1.29 к цене
соседей, уровня 5 → ×2.16; инфинити-бассейн → ×1.52 (есть у 1% рынка);
полный вид на океан → ×1.46; отсутствие бассейна → ×0.84; рабочий стол → ×1.00.

Прогон: `node scripts/booking-vision.mjs --conc=40` (докатывает остаток,
разобранное пропускает), каталог — `node scripts/catalog-vision.mjs` плюс
`node scripts/catalog-vision-load.mjs` для заливки в таблицу.
Цена вопроса — около $0.01 за объект при 6 фото.

**Гочи.** Карточки с битыми фото на CDN Booking (снятые с продажи объекты)
не разбираются никогда — это ~4 тыс. записей, среди них почти нет объектов
с ценой и загрузкой. Наши ЖК модель видит по рендерам, а рынок — по реальным
снимкам, поэтому оценки «качества картинки» (отделка, цельность дизайна,
инстаграмность) у каталога завышены системно; сравнивать каталог с рынком можно
только по структурным признакам (открытая гостиная, кровля, сала, тип бассейна).
