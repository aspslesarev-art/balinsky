# Investment Widget

Виджет «Инвестиционный потенциал виллы». Считает три сценария
доходности (плохой / нормальный / хороший) на основе матчинга
с конкурентами Booking и анализа района.

## Интеграция

```tsx
import { InvestmentWidget } from '@/components/InvestmentWidget'

// На странице виллы:
<InvestmentWidget villaId={airtableId} apiKey={GOOGLE_MAPS_KEY} />
```

Виджет сам подгружает `/api/villa/[id]/investment-snapshot` и
рендерит весь блок.

## Архитектура

```
GET /api/villa/[id]/investment-snapshot       (cache 24h)
  → lib/investment/snapshot.ts: buildSnapshot(id)
      → lib/competitors.ts: loadNearby(lat, lng, 2km)
      → lib/nearby-places.ts: loadNearbyPlaces(id)
      → lib/investment/zones.ts: classifyZone(beaches)
      → lib/investment/matching.ts: matchCompetitors(...)
      → lib/investment/economics.ts: buildScenarios(...)
      → lib/investment/infra-score.ts: scoreInfra(...)
      → возвращает InvestmentSnapshot
```

## Режимы виджета

| N матчей | Режим | Что показывает |
|---|---|---|
| ≥ 12 | `standard` | Три сценария по квартилям ADR + полная статистика. Уверенность 🟢 |
| 5–11 | `reduced` | Те же три сценария, помечены 🟡 «средняя уверенность» |
| < 5 | `references` | Не агрегируем — даём 3-5 конкретных примеров с Booking |

Если в исходной зоне до пляжа 0 матчей — расширяем зону на одну
ступень (beachfront → walking → scooter → inland). Помечаем
флагом `expandedZone` и показываем баннер.

Для вилл с 5+ спален — luxury-режим: матчинг без зонального
ограничения (премиум-гость выбирает по объекту, не по геолокации).

## Флаги

- `emergingMarket` — если в радиусе 1км менее 30 листингов на
  Booking. Триггерит блок «Новый район».
- `weakPerformance` — если cap rate в плохом сценарии ниже
  порога региона (Bali: 1,5%). Порог относительный: после перехода
  на полный водопад расходов медианная чистая доходность новостроя
  Бали около 2%, и прежние 6% помечали бы весь рынок без разбора.
- `leaseholdRisk` — если payback > leasehold_years_left. Красный
  баннер. Отдельно `capitalReturned === false` показывает, что за
  оставшийся срок права аренды объект не возвращает вложенное
  вообще — это не «медленно окупается», а «не окупается».
- `isLuxury` — 5+ спален. Влияет на матчинг.
- `expandedZone` — пришлось выйти за исходную пляжную зону.

## Юнит-экономика

```
adr           = ADR_из_выдачи × realization    (скидки за длинный stay, промо)
revenue       = adr × 365 × occupancy
platform_fee  = revenue × 16%          (Booking/Airbnb, рынок 15–17%)
phr_tax       = revenue × 10% × доля_на_владельце
mgmt_fee      = revenue × 17%          (управляющая компания, рынок 13–20%)
opex          = max($4/м²/мес × area × 12, floor_base + floor_per_bed × bedrooms)
  разбивка: электричество и вода 30%, уборка и персонал 30%,
  расходники гостям 25%, бассейн и сад 8%, интернет/газ/мелкий ремонт 7%
  (доли от итоговой суммы; последняя статья добирает остаток округления,
  поэтому разбивка сходится с общей строкой до цента)
ffe_reserve   = revenue × 4%           (износ мебели, техники, текстиля)
pbb_tax       = asking_price × 0,1%    (налог на землю и здание: 0,2% от
                                        NJOP при NJOP около половины рынка)
pre_tax       = revenue − platform_fee − phr_tax − mgmt_fee − opex
                − ffe_reserve − pbb_tax
tax           = max(0, pre_tax) × (10% резидент | 20% нерезидент)
NOI           = pre_tax − tax

entry_price   = asking_price + closing (5%) + furnishing ($80/м², если не меблирован)
payback       = entry_price / NOI
cap_rate      = NOI / entry_price
leasehold_irr = IRR потока (−entry_price, NOI × N лет, терминал 0)
```

Блок «Как считалось» в виджете раскрывает весь водопад целиком: каждую
статью расходов с её долей, разбивку операционных расходов по статьям,
оба налога и подписи, откуда взят каждый процент. Ничего не считается
за кадром — покупатель может проверить любую строку вручную.

Доходность считается **от цены входа, а не от прайса**: покупатель
платит ещё за оформление и меблировку, и не учитывать их — значит
завышать процент. `NOI` и `entry_price` округляются до вычисления
`cap_rate`, чтобы разбивка в виджете сходилась при проверке вручную.

Дефолты в `lib/investment/regions.ts:BALI_DEFAULTS`. Пока
поддерживается только Бали.

### Откуда взялись коэффициенты

Из аудита 814 объектов новостроя против 14 898 объектов аренды
(август 2026). Модель проверена контролем через помесячную аренду
на одинаковых парах район + число спален: медиана отношения
посуточной выручки к долгосрочной — 1,0–1,1, валовая доходность
двумя независимыми способами сошлась на 6–8%.

Комиссии УК (13–20%), канальные (15–17%), налоги (PHR 10%,
PPh 10%/20%) и операционные расходы взяты из рыночных источников;
базовый минимум расходов калиброван по замеру для трёхспальной
виллы в Улувату — IDR 6,3–9,5 млн/мес.

## Дефолтные occupancy для Бали

Booking не отдаёт occupancy конкурентов, а метрика в источнике
считает «дату нельзя забронировать», а не «дату продали», и
снимается в пик сезона — её медиана по зонам 87–96%, что для
годовой загрузки нереально.

Поэтому загрузка привязана к отраслевому ориентиру по Бали
(55–65% годовых, 70–80% у лучших объектов «золотого треугольника»):

- bad = 50%
- median = 60%
- good = 70%

Это не значения конкретных конкурентов, а рыночные оценки.
Указано в блоке «Методология».

## Налоговый статус

Переключатель в калькуляторе: резидент с индонезийским NPWP платит
10%, нерезидент — 20% (PPh 26). По умолчанию **нерезидент** —
консервативная сторона и статус большинства покупателей.
Ранжирование каталога (`batch-scores.ts`) считается только для
нерезидента: налог сдвигает все cap rate примерно одинаково и на
порядок объектов не влияет.

## Зоны до пляжа

Walking-distance считается как `Haversine × 1.3` (без OSRM):

- `beachfront` — 0–100 м
- `walking` — 100–500 м
- `scooter` — 500–1500 м
- `inland` — >1500 м

## Скоринг инфраструктуры

В радиусе 800 м от виллы считаем:

- Premium-рестораны (priceLevel ≥ EXPENSIVE и rating ≥ 4.3) → вес 25
- Beach clubs → вес 20
- Топ-кофейни (rating ≥ 4.5) → вес 15
- Fitness/yoga/wellness → вес 10
- Ночные клубы → вес 10
- Средний рейтинг POI (нормализован 3.8→4.8) → вес 10
- Плотность отзывов → вес 10

Композитный балл 0–100.

## Кэширование

- API endpoint: `Cache-Control: s-maxage=86400, stale-while-revalidate=604800`
  (24 часа полная свежесть, 7 дней stale-while-revalidate).
- На сервере есть module-level кэш для манифестов конкурентов и
  POI (TTL 10–30 мин).

## Тесты

Базовые юнит-тесты на чистые функции (zones, economics):

```bash
node --experimental-strip-types --test scripts/test-investment.mjs
```

Экономика импортируется из продового модуля напрямую. Раньше
формула была продублирована в тесте со своими константами — такой
тест проверял сам себя и остался бы зелёным при любой правке модели.

Покрытие:
- `classifyZone` (beachfront/walking/inland)
- standard / reduced / references mode по размеру выборки
- emerging market по плотности листингов
- leasehold warning, невозврат капитала, IRR и freehold-случай
- weak cap rate
- сходимость водопада: выручка − расходы = прибыль − налог = NOI
- реализация ставки, цена входа, меблировка, пол расходов
- налог резидента против нерезидента, отсутствие налога с убытка
- null-кейс без asking price

## Что не реализовано (по сравнению со спеком)

- **Сценарий «без обновления через 5 лет»** — нет года ремонта в Airtable.
- **Forward booking 90d / asking ADR новых ЖК** — нет источника данных.
- **OSRM walking distance** — используется Haversine × 1.3.
- **Per-competitor occupancy** — Booking не отдаёт; используются
  фиксированные дефолты по сценариям.

## Что поправить, если расширять

- Добавить поле `Год ремонта` в Airtable → включить сценарий деградации.
- Подключить Inside Airbnb / AirDNA → реальная occupancy.
- Развернуть OSRM в Docker → точная walking distance.
- Добавить регионы помимо Бали — расширить `lib/investment/regions.ts`.
